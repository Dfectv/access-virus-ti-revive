USB side: the OUT endpoints' byte-count registers (0xFF83 for the small vendor endpoint, 0xFF7B for the 32-byte one; data at 0xFED0 / 0xFEE8) are read by the USB interrupt handler (0x0430); the packets are copied (0x18f1) into a 64-byte ring at 0xFE50 (INTMEM 0x5E read / 0x5F write index, masked 0x3F) only if at least 32 bytes are free, otherwise the count register is left set, so the chip keeps answering NAK and nothing is dropped on the USB side. The 8052 UART (SCON 0x92: mode 2, 9-bit, SMOD 0 = MCU clock/64) sends the ring 4 bytes per frame with the 9th bit set on the first byte (= one USB-MIDI event packet per frame, serial ISR 0x13e7) and appears to transmit only while the input T0 (P3.4) is high (decompiler output unclear, MED); received frames (9th bit = frame start) go to INTMEM 0x9E-0xA1. Host side: a serial channel at SFR 0x9A (status: bit 0 receive, bit 1 transmit, bit 2 received 9th bit, bit 3 9th bit to send) / 0x9B (data), ISR 0x3288 at vector 0x4B: a frame lands in INTMEM 0xC8-0xCB (0xC8 = cable << 4 | CIN) and goes to 0x286d / 0x28e7; if fewer than 8 bytes are free in the destination ring the packet is parked (state 99, XDATA 0x04F7 counts (mod 128)) and taken by the main loop 0x14e4 once 12 bytes are free - a frame arriving meanwhile replaces it (loss). Transmit: 4-byte packets from the queue XDATA 0x6C00-0x6FFF (256 entries in four 256-byte columns, write index INTMEM 0x3D, read 0x3E), 9th bit on the first byte; the host toggles P1.1 after each received frame (handshake candidate, open). Dispatch by cable (0x28e7, bytes per CIN as in the USB-MIDI class): 0 -> DIN MIDI out ring (0x281b); 3 -> the host's MIDI parser ring (0x277c); 5 -> straight to both DSPs (0x605b writes command 0x39 and the byte to the host ports at XDATA 0x0000-0x0007 and 0x0100-0x0107, no ready check); the remaining cables (2) -> parser ring and both DSPs. This matches E025/E033 (cable 2 channel messages, 3 SysEx, 5 F5 stamps) and says why F5 stamps never show in the host's own state: they go to the DSPs only.
